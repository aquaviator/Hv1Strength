# Pilot Export Specification

Status: specification only. No production export is generated by this integration.

## Purpose

A future, separately authorised export may project approved catalogue candidates into the current Android `Exercise` shape without exposing planning metadata as application features.

## Allowed fields

The export contains exactly:

| Field | Type | Rule |
|---|---|---|
| `id` | String | Separately allocated existing-style production identifier; never copied automatically from `catalogue_key` |
| `name` | String | Approved manifest `canonical_name` |
| `category` | String | Approved Pilot 1.0 compatibility category |
| `isCustom` | Boolean | Always `false` for seeded catalogue exercises |

No other manifest field is exported. In particular, aliases, substitution groups, equipment, muscles, movements, difficulty, technical complexity, facility tier, commercial metadata, module tags, and review data remain catalogue-only.

## Identity boundary

- Preserve every existing production exercise ID unchanged.
- `catalogue_key` is planning-only and must not become `id`, `globalId`, a UUID, or a Firestore document ID.
- Production IDs require a separate allocation and collision-review process.
- This specification does not define a Room seed update, Firestore document, JSON format, or import command.

## Category boundary

Use only the temporary mappings recorded in `SCHEMA-ALIGNMENT.md`. Candidates from Olympic Weightlifting, Strongman, Conditioning, or Strength-Relevant Mobility remain outside Pilot 1.0 unless human review finds a clean, unambiguous mapping.

## Example policy

No example export file is included. The ten demonstration manifest rows remain architecture test data and are not production candidates or allocated records.
